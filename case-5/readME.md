# Аналитический обзор WEB-приложения «Система управления туристическими заказами»
## Кейс-задача № 4 (на основе Delphi 10.2 + IIS + MS SQL Server)

---

### 1. Введение

В рамках кейс-задачи № 4 было разработано WEB-приложение на платформе **Delphi 10.2 Tokyo** с использованием **Microsoft IIS** и **MS SQL Server**. Приложение представляет собой ISAPI-библиотеку (DLL), предоставляющую REST API и веб-интерфейс для управления туристическими заказами. В данном обзоре проведён анализ разработанного решения по девяти ключевым критериям качества программного обеспечения, выявлены проблемные зоны и предложены способы их решения.

---

### 2. Оценка по критериям качества

#### 2.1. Функциональность (оценка: 7/10)

**Описание:**  
Приложение реализует базовый набор функций для работы с туристическими заказами:
- Просмотр списка туров, клиентов, стран.
- Просмотр заказов (всех или по клиенту).
- Создание нового заказа через HTTP-параметры.
- Вывод данных в форматах HTML и JSON.

**Выявленные проблемы:**
- Отсутствие операций CRUD для справочников (нет возможности добавлять, редактировать или удалять туры, клиентов и страны через интерфейс).
- Нет валидации входных данных на стороне сервера (например, проверка существования клиента и тура при создании заказа).
- Отсутствие фильтрации и поиска (нельзя отфильтровать заказы по дате, статусу или диапазону цен).
- Нет поддержки обновления и удаления заказов (заказ нельзя отменить или изменить).

**Предложения по улучшению:**
- Реализовать REST-методы для CRUD-операций:
  - `POST /tours` — создание тура.
  - `PUT /tours/{id}` — обновление тура.
  - `DELETE /tours/{id}` — удаление тура.
- Добавить валидацию:
  - Проверка существования `client_id` и `tour_id` перед созданием заказа.
  - Проверка корректности даты (не в прошлом).
- Внедрить фильтрацию через параметры запроса:
  - `/orders?status=Оплачен`
  - `/orders?date_from=2025-01-01&date_to=2025-12-31`
- Добавить поддержку `PATCH` для изменения статуса заказа.

#### 2.2. Производительность (оценка: 6/10)

**Описание:**
Приложение работает как ISAPI-модуль, что обеспечивает высокую производительность благодаря нативному коду Delphi. Однако есть узкие места.

**Выявленные проблемы:**
- Отсутствие кэширования — каждый запрос выполняет полноценный SQL-запрос к БД.
- Загрузка всех данных без пагинации при выводе таблиц.
- Отсутствие индексов в базе данных на внешних ключах и часто используемых полях.
- Последовательная обработка — нет асинхронности или параллельной обработки запросов.

**Предложения по улучшению:**
- Добавить **кэширование** на уровне приложения:
  - Справочники (страны, клиенты) кэшировать на 5–10 минут.
  - Использовать `TTimer` для автоматического обновления кэша.
- Внедрить **пагинацию**:
  - Параметры `?page=1&limit=50` в запросах.
  - В SQL использовать `OFFSET ... FETCH NEXT`.
- Создать **индексы** в MS SQL Server:

CREATE INDEX IX_Orders_client_id ON Orders(client_id);
CREATE INDEX IX_Orders_tour_id ON Orders(tour_id);
CREATE INDEX IX_Orders_start_date ON Orders(start_date);
CREATE INDEX IX_Tours_country_id ON Tours(country_id);

Использовать пулы соединений (в FireDAC они уже есть, но можно настроить параметры).

Для вывода больших таблиц использовать виртуальный режим (постраничная загрузка через JavaScript).

#### 2.3. Удобство использования (юзабилити) (оценка: 5/10)
Описание:
Интерфейс представлен в виде HTML-страниц с таблицами, что обеспечивает базовую навигацию. Однако пользовательский опыт оставляет желать лучшего.

Выявленные проблемы:

Минималистичный дизайн — только HTML с базовым CSS, нет адаптивности.

Отсутствие форм ввода — для создания заказа нужно вручную формировать URL с параметрами.

Нет сообщений об ошибках на русском языке (пользователь видит техническую информацию).

Нет подтверждения действий — после создания заказа нет возврата к списку с уведомлением.

Отсутствие навигации между разделами — пользователь должен использовать кнопку «На главную».

Предложения по улучшению:

Разработать SPA-интерфейс на React или Vue.js (легко интегрируется через REST API).

Добавить формы для:

Создания заказа с выпадающими списками клиентов и туров.

Поиска и фильтрации.

Внедрить интерактивные уведомления (toast-сообщения) о результатах операций.

Улучшить адаптивность под мобильные устройства (использовать CSS-фреймворк Bootstrap).

Добавить хлебные крошки и меню навигации.

####2.4. Безопасность (оценка: 4/10)
Описание:
Приложение имеет серьёзные уязвимости, характерные для многих учебных проектов.

Выявленные проблемы:

Отсутствие аутентификации и авторизации — любой пользователь может просматривать и изменять данные.

Отсутствие защиты от SQL-инъекций — хотя FireDAC использует параметризованные запросы, в некоторых местах возможна подстановка.

Отсутствие HTTPS — данные передаются в открытом виде.

Нет валидации входных данных — можно передать отрицательную цену или некорректную дату.

Нет логирования действий — невозможно отследить, кто и что изменял.

ISAPI-модуль имеет права на уровне системы, что может быть опасно.

Предложения по улучшению:

Внедрить аутентификацию через Windows Authentication (IIS) или собственный механизм на основе JWT.

Все входные параметры экранировать и валидировать:

function ValidateDate(DateStr: string): Boolean;
begin
  Result := TryStrToDate(DateStr, Date) and (Date >= Date);
end;

Настроить HTTPS в IIS (создать самоподписанный или купить SSL-сертификат).

Добавить логирование всех действий:

uses System.IOUtils;
procedure LogAction(const User, Action: string);
begin
  TFile.AppendAllText('log.txt', Format('[%s] %s: %s'#13#10, [DateTimeToStr(Now), User, Action]));
end;

Настроить права доступа IIS для ограничения возможностей ISAPI-модуля.

Использовать параметризованные запросы для всех операций (уже есть в DataModule.pas, но проверить все места).

####2.5. Масштабируемость (оценка: 5/10)
Описание:
Текущая архитектура имеет ограниченную масштабируемость.

Выявленные проблемы:

Монолитная архитектура — вся логика в одной DLL.

Ограниченная горизонтальная масштабируемость — ISAPI-модули сложно распределять.

Нет балансировки нагрузки.

Единая база данных — не разделена на чтение и запись.

Предложения по улучшению:

Переход на микросервисную архитектуру:

Сервис туров.

Сервис клиентов.

Сервис заказов.

Использовать репликацию БД (master-slave) для распределения нагрузки.

Внедрить кэширование на уровне Redis.

Использовать контейнеризацию (Docker) для упрощения масштабирования.

Для высоких нагрузок рассмотреть переход с ISAPI на самостоятельное серверное приложение (exe) с использованием TIdHTTPServer.

####2.6. Сопровождаемость (оценка: 6/10)
Описание:
Код написан с использованием стандартных практик Delphi, имеет базовые комментарии.

Выявленные проблемы:

Нет модульных тестов.

Ограниченная документация — комментарии есть только в DataModule.pas, WebModule.pas не документирован.

Жёсткое связывание с базой данных — изменения в структуре БД требуют изменений в нескольких местах.

Нет использования паттернов проектирования.

Смешение логики — методы работы с БД и генерации HTML в одном модуле.

Предложения по улучшению:

Внедрить паттерн Repository для абстракции доступа к данным.

Разделить логику:

BL/*.pas — бизнес-логика.

DAL/*.pas — доступ к данным.

UI/*.pas — генерация HTML/JSON.

Написать модульные тесты с использованием DUnitX.

Создать документацию в формате Markdown для всех публичных методов.

Использовать интерфейсы для слабой связанности.

Внедрить инъекцию зависимостей (например, через конструкторы).

####2.7. Переносимость (оценка: 4/10)
Описание:
Приложение жёстко привязано к экосистеме Microsoft.

Выявленные проблемы:

Привязка к Windows — Delphi 10.2 поддерживает Windows и (частично) Linux, но ISAPI работает только на IIS/Windows.

Привязка к MS SQL Server — использование MSSQL-специфичного синтаксиса.

Не кроссплатформенный интерфейс — HTML-генерация не зависит от ОС.

Предложения по улучшению:

Использовать FireDAC с поддержкой разных СУБД (переключение между драйверами).

Переписать SQL-запросы с использованием ANSI SQL (избегать специфичных конструкций).

Для кроссплатформенности использовать Self-Hosted приложение (EXE) на Linux с TIdHTTPServer.

Вынести конфигурацию подключения в внешний файл (.ini или .json).

Использовать Docker-образы для упрощения развёртывания на разных платформах.

####2.8. Качество кода (оценка: 6/10)
Описание:
Код написан структурированно, но есть недостатки.

Выявленные проблемы:

Дублирование кода — генерация HTML и JSON дублируется.

Длинные методы — WebModule1DefaultHandlerAction и другие.

Магические строки — URL-пути и названия параметров не вынесены в константы.

Смешение языков — SQL в коде (хотя через параметры).

Нет обработки исключений — ошибки падают в IIS без понятного сообщения.

Предложения по улучшению:

Создать утилитарные классы:
THTMLGenerator.GenerateTable(DataSet);
TJSONGenerator.Generate(DataSet);

Вынести константы:
const
  C_ACTION_TOURS = '/tours';
  C_PARAM_CLIENT = 'client';
  
  Добавить обработку ошибок с возвратом HTTP-статусов:
  try
  // код
except
  on E: Exception do
  begin
    Response.StatusCode := 500;
    Response.Content := '{"error":"' + E.Message + '"}';
  end;
end;

Использовать форматирование кода (форматер CodeTyphon).

Разбить длинные методы на подфункции.

####2.9. Тестирование (оценка: 3/10)
Описание:
Тестирование проведено минимально — только ручная проверка основных сценариев.

Выявленные проблемы:

Нет автоматических тестов.

Нет тестирования производительности.

Нет тестирования безопасности.

Нет тестирования на граничных значениях.

Предложения по улучшению:

Создать набор интеграционных тестов с использованием TIdHTTP:
procedure TestGetTours;
var
  HTTP: TIdHTTP;
  Response: string;
begin
  HTTP := TIdHTTP.Create(nil);
  try
    Response := HTTP.Get('http://localhost/TourismApp.dll/tours?format=json');
    // Проверка, что Response содержит "Tours" и не пустой
  finally
    HTTP.Free;
  end;
end;

Внедрить непрерывное тестирование с использованием CI/CD (GitHub Actions).

Провести нагрузочное тестирование (Apache JMeter, ab или wrk).

Добавить тесты безопасности (проверка SQL-инъекций, XSS).

Создать чек-лист ручного тестирования для регрессионного тестирования.

####5. Заключение
Разработанное WEB-приложение представляет собой рабочую систему управления туристическими заказами, демонстрирующую базовые возможности Delphi 10.2 в сочетании с IIS и MS SQL Server. Однако проведённый анализ выявил ряд недостатков, характерных для прототипов: низкая безопасность, отсутствие автоматических тестов, неудобный интерфейс и ограниченная функциональность.

Основные рекомендации по улучшению:

Усилить безопасность — добавить аутентификацию и HTTPS.

Развить интерфейс — создать SPA с удобными формами.

Внедрить тестирование — покрыть код модульными и интеграционными тестами.

Улучшить сопровождаемость — переработать архитектуру с использованием паттернов.

Реализация предложенных улучшений позволит превратить прототип в промышленное решение, готовое к использованию в реальной корпоративной среде. При этом ключевые преимущества платформы Delphi (производительность, нативный код, тесная интеграция с Windows) будут сохранены и усилены.
